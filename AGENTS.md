# Toybox Studio Agent Guide

Operational guide for AI agents working in the Toybox Studio repository. Studio is the C#/Avalonia (MVVM, .NET 10) editor that drives the C++ Toybox engine over RPC. AI-generated code is held to the **same standards as human-written code** and is reviewed with great care — see [`Documentation/Contributing.md`](Documentation/Contributing.md).

## Standards

**Strictly follow [`Documentation/CodeStandards.md`](Documentation/CodeStandards.md).** It is the single source of truth for C#/Avalonia engineering policies, MVVM rules, file/class layout, and formatting. Do not restate those rules here — keep `Documentation/` up to date when making sweeping architectural changes.

Most-violated reminders (full rules live in CodeStandards):

- **MVVM only — no code-behind routing.** No view-model bootstrap or event wiring in `.axaml.cs`. Use commands, attached behaviors (`Behaviors/`), control subclasses, and services instead.
- **One class per `.cs`, one widget per `.axaml`.** Don't mash multiple types into a file.
- **Don't suffix shared parent classes with `Base`.** Name a type for what it is (e.g. `DropdownPropertyViewModel`, not `PropertyViewModelBase`).
- **Return `Result`/`Result<T>` for expected failures** (RPC calls, project/file operations) instead of throwing; the build treats warnings as errors and nullable is enabled.
- **Prefer existing editor utilities and the simplest direct solution** over new abstractions. Panels are self-contained; avoid god classes.
- **Compiled bindings are on by default** — bindings must be statically resolvable (`x:DataType`).

## Repository Map

**Flat feature folders at the repo root** — there is no longer a `Services/` or `Widgets/` tier folder. Namespaces follow folders exactly (`Toybox.Studio.<Feature>`, e.g. `Toybox.Studio.EngineApi`). A feature folder co-locates its model, view-model, and view (the `Entity` / `EntityViewModel` / `EntityView` shape); plain data types live beside the construct that owns them (there is no separate `Models/` tier). The old tier *dependency direction* — pure `Utils/` → engine/domain services → `Shell/` → UI panels — remains a design convention (lower never depends on higher), just no longer a folder boundary.

**Naming**: view-models end in `ViewModel`, views end in `View` (dialogs/windows keep the `*Dialog`/`*Window` sub-convention), models are bare (`Entity`, not `EntityModel`). A type must not share the name of its own folder/namespace leaf (that shadows the type from sibling namespaces) — hence `Worlds/`, `Clipboards/`, `ColorPickers/`, and `Game/` are named to avoid the clash with the `World`/`Clipboard`/`ColorPicker`/`GameView` types.

Foundation:

- `Utils/` — pure, dependency-free helpers: `Result.cs` (the failure type used everywhere), `Dispatch.cs`/`DispatchContext.cs` (UI-thread marshalling), `Contrast.cs` (WCAG contrast maths), `IListenable.cs` (the change-notification contract). Extension classes live in `Utils/Extensions/`; the cross-layer marker attributes (`[Hidden]`, `[Icon]`, `[Dockable]`) in `Utils/Attributes/`.

Engine, domain & editor services (formerly `Services/`):

- `Rpc/` — the **generic transport**, peer-agnostic: `RpcClient.cs` (newline-delimited JSON-over-loopback-TCP `JsonRpc`, connect-with-retry, `InvokeAsync`/`NotifyAsync` primitives, `Disconnected` event — knows nothing about the engine's methods), `RpcHandlers.cs`, `RpcCall.cs` (a data-driven call run by `EngineRpc.RunAsync`; the building block of a toolbar `ToolCommand`).
- `EngineApi/` — `EngineRpc.cs` (the **engine connection**: a thin engine-specific facade over an `RpcClient` — the `editor.hello` handshake, typed inbound-notification events, engine-lifecycle/viewport calls, and the `InvokeAsync`/`NotifyAsync` forwarders the domain builds on; every request is **guarded** → failure `Result` and **bounded** by a default timeout, so callers pass `CancellationToken.None` safely; VMs never hold the raw client), `Session.cs` (launch-owned vs attach, ping loop, watchdog, teardown — delegates the native build to `ProjectBuilder`), `EngineLocator.cs`, `EngineWatcher.cs`, `InstanceDetector.cs`, `ViewportStream.cs`, plus the **engine-sync layer** the codegen drives: `EngineSyncAttribute.cs` (`[EngineSync(syncCommand, syncMode, converter, batchFrequencyMs, engineParams…)]` on partial properties/methods — see its doc comment for the full API), `EngineObject.cs` (the sync base the generator *injects* — user code never inherits it by hand; models notify via `IListenable`, anything view-bound gets an explicit view-model; every engine object is also `ISerializable` — `Serialize()`/`Deserialize()` round-trip the synced body for the clipboard, Mirror values excluded so a copied body carries content, never identity), `SyncHub.cs`/`SyncScheduler.cs` (binding, inbound `sync.changed` routing, Live/Batched/Manual outbound timing), `EngineAddress.cs` (the wire identity, declared as an `Address = "entity/{EntityId}/{Name}"` template on the class-level attribute and generated from there), `WireValue.cs` (the built-in codecs, over the shared wire value types `Handle`/`Size`) + `IWireConverter.cs` (the per-member escape hatch, with the reusable `HandleListConverter`/`StringListConverter`/`SizeConverter`), and `SyncSlot.cs`. The generator lives in `Generators/` (netstandard2.0, consumed as an analyzer via `OutputItemType="Analyzer"`) and keys on the `Toybox.Studio.EngineApi.EngineSyncAttribute` metadata name.
- `Ecs/` — the entity/component domain, built on the engine-sync codegen: `Entity.cs` (synced properties + generated structural commands), `Component.cs` (the family root whose class-level `[EngineSync]` sets the `component.set` default and roots the hierarchy), and the full concrete component set mirroring the engine's `tbx/types/components` headers (`Transform`, `Renderer`, `Camera`, the light family, colliders + the `Trigger` family, `Rigidbody`, `Sky`, `PostProcessing`, `Lods`, `Particles`, `ScriptContainer`) together with their nested value records (`Viewport`, `Lod`, `PostProcessingEffect`, …) and `IWireConverter`s. The world-family assets also live here — `World`, `WorldChunk`, `WorldGlobals` (`: Asset`, from `Assets/`) — because the latter two contain `Entity` registries (`EntityListConverter` carries each entry's id — a registry entry IS identity, unlike a copied body) and `Ecs` already depends on `Assets`, so the reverse reference would be circular. Domain objects raise `IListenable.Changed` only; the world tree and inspector bind to explicit view-models (to come with those panels).
- `Assets/` — the asset domain, mirroring the engine's `tbx/types/assets` headers on the same codegen: `Asset.cs` (the family root — the `asset.set` default plus the `asset/{Id}` address; identity/version are Mirror, so a serialized body carries content, never identity), the typed payloads (`Material`, `MaterialInstance`, `Texture`, `Shader`, `Model`, `AudioClip`; the world family lives in `Ecs/` — see above), and the record values they carry (`ShaderProgram`, the parameter/texture bindings, `MaterialConfig`, `MaterialOverrides`) with their converters. Nested values are immutable records — edit by assigning a changed copy back to the synced property, which is what pushes it (in-place mutation is invisible to the sync layer); `MaterialInstance` wraps that rule in the C++-style typed setters (`SetFloat`/`SetTexture`/`GetFloatParameterOr`, …) and doubles as a by-value component field (a `Sky`'s material) via `MaterialInstanceConverter`. The asset **pipeline** lives here too: `AssetCatalog.cs` (the handle database over `editor.listAssets` — `AssetEntry` rows, self-refreshing on connect, each swap dispatched as an `AssetCatalogChanged` event), and the whole lifecycle is the constructor plus `SaveAsync()` on `Asset` itself (there is no factory or type table): `new Material(id)` IS the load — the mirror binds to the `SyncHub` and hydrates itself via `sync.describe` (await `asset.Loaded` to observe it; failures log and leave it unbound) — while `new Material("Sky", "Materials")` is a fresh asset carrying the location its first `SaveAsync()` authors it at through `asset.create` (gated by the payload's own `[Creatable("mat")]` declaration: the created file's extension rides on it, and the engine type name is the payload type's name); every save after that persists normally. Assets carry an assignable `Name`/`Path` file identity (populated from the catalog on load): the save payload carries the current `Path`, so assigning either renames/moves the file on the next save. The lifecycle's services are wired once by the composition root via `Asset.Configure(hub, catalog, log)`. Persisting is the asset's own `Asset.SaveAsync` (flush staged edits, then `asset.save` by address); every asset carries `IsDirty` — set by any bound edit (the `EngineObject.OnEdited` seam; unbound assignments and inbound applies don't count), cleared by a successful save.
- `Worlds/` — the editor-session world tools; today, the transform tool: `GizmoTool` (the one source of truth for the active `GizmoMode` — Select shows the combined "super" gizmo — and the snapping toggle: registers the `gizmo.*` editor actions, executes their `EditorActionInvoked`, announces each change as a `GizmoToolChanged`, and pushes the active tool to the engine over `view.setGizmo` on every change and (re)connect) and `TransformGizmo` (the editor-authored gizmo looks: each mode's handle set — `GizmoHandle` kind/axis/extent for the engine's interaction + a unit-space `GizmoRenderer` op stream for the visuals, built on the Gizmos drawing API; the engine replays the ops under the pivot/screen-size frame and hit-tests the declared shapes). Snapping is `enabled XOR snap-hold-key-held` engine-side: the snap-hold binding (`gizmo.snapHold`, Ctrl by default) lives in the keymap and rides to the engine as key codes, the steps in `EditorSettings.Gizmos`. (The world asset + `WorldSelection` live in `Ecs/`.)
- `Project/` — `ProjectManager.cs`, `CMakeCompiler.cs`, `ProjectBuilder.cs` (native build/ship orchestration, separate from the `Session` that runs the result), `AssetCatalog.cs` (the handle database + reflection-discovered `AssetTypes`), `AssetFactory.cs`, `Asset.cs` (the abstract asset handle that IS the asset API — static `Asset.For`/`Asset.Of` construction, instance `Load/Save/Open/Rename/Delete/Duplicate/Copy`, `CreateAsync` + `Creatable`, `CanPaste`/`Paste`), `AssetServices.cs` (the DI singleton bundling the services a handle needs), and `Project/Assets/` (the strongly-typed `Asset`/`AssetData` subclasses — `Material`/`MaterialInstance`/`Texture`/`Model`/`Script`/`Shader`/`UnknownData` + the `ProjectSettings` settings asset).
- `Settings/` — the editor's persisted configuration in two halves, both owned by `SettingsManager.cs`: the plain `EditorSettings` data (EditorSettings.json in ~/.toybox, loaded at construction, written by `SaveAsync` — the mutate-then-save commit point, each save dispatching one `EditorSettingsChanged`) and the open project's `AppSettings` — an engine-mirrored asset (`: Asset`, on the same EngineSync codegen as `Assets/`) whose `GraphicsSettings`/`WorldSettings`/`PhysicsSettings`/`AsyncSettings` records + converters mirror the engine's `tbx/systems/*/settings.h`. The manager tracks the project's `AppSettings.json` through the `AssetCatalogChanged` event: the row appearing loads the mirror (exposed as `App`), the listing emptying on disconnect drops it, and each swap dispatches one `AppSettingsChanged` (`SettingsEvents.cs`); edits push live like any asset's and persist through the asset's own `SaveAsync`.
- `Keybindings/` — the rebindable action layer: `ActionRegistry` (every invokable editor action as an `EditorAction` — stable id from the `ActionIds` consts, title/category/icon, scheme scope, default chords; features register theirs at construction), `EditorKeymap` (the actions' bindings as a real `.inputmap` — the same engine asset format game input maps use — at `~/.toybox/EditorKeybindings.inputmap`; the in-memory map is registry defaults overlaid with the file, so new actions appear bound to their defaults while user chords survive), `KeybindingDispatcher` + the `KeybindingScope` attached behavior (the main window's tunneling key handler: chord → matched action → one `EditorActionInvoked` through the event bus — menus publish the same event, so keyboard and menu are a single invocation path; schemes scope per focused dockable, text inputs keep their bare keys, and the engine viewport keeps them only while navigating — a pointer button held — otherwise its own scoped bindings may claim them (the gizmo Q/W/E/R), never global ones; bare modifier key-downs never dispatch, they are hold-state), and `KeyChordGestures` (engine chord ↔ Avalonia `KeyGesture`, derived from `EngineInputTranslator.Map` so the directions can't disagree).
- `Theming/` — merges the theming service and its UI: `ThemeManager.cs` (facade) + `ThemeRepository.cs` + the appliers + `Theme.cs`/`ColorGradient.cs`, plus the `ThemeCreatorWindow`/`ThemeCreatorViewModel`.
- `Dialogs/` — merges the dialog services (file/asset pickers, popups, OS reveal) with the MVVM dialog widgets (`ConfirmDialog`, `MessageDialog`, `AssetPickerDialog`, …).
- `Scripting/` (`ScriptService`/`ScriptCatalog`/`ScriptDocument`), `Clipboards/` (the `Clipboard` service — a JSON envelope over the OS clipboard that copies plain values and engine-synced object bodies with no per-kind wrapper types), `Favorites/`, `Logging/` (`Logger.cs` unified editor+engine log, `LogFile.cs`).

App frame & UI (formerly `Shell/` + `Widgets/`):

- `Shell/` — `MainWindow` + `MainWindowViewModel` (menu bar over the dockable workspace over the status bar); `Styles/` holds the split XAML sheets aggregated by `AppStyles.axaml`.
- `Workspaces/` — the docking system over vanilla Dock.Avalonia: `DockableCatalog` reflection-scans the feature assemblies for `[Dockable]` Views and pairs each with the view-model factory the composition root authored in `DockableFactories` (view-models are NEVER service-registered — a panel's lifetime belongs to the workspace: singleton panels focus-or-open, non-singletons spawn a fresh disposable view-model per open), `Workspace` deals purely in windows and owns the dockable registry + open-instance table — query via `All`/`Opened`/`Docked`/`Floating`/`Closed`/`Find`, act via `Open`/`OpenOrFocus`/`Focus`/`Close`, plus the runtime panel lifecycle (`DockTree`/`OwnerTabBinder` are its query/binding helpers) — and `LayoutManager` owns layouts as a whole: building the default from each dockable's `DockSlot` (Top/Left/Right/Bottom edges, optionally relative to a `Parent` dockable; `Float` opens as a floating window at the attribute's declared bounds), rehydrating/healing saved ones, and persisting them through the `LayoutStore` it owns under `~/.toybox/Layouts`. Neither class IS a Dock factory: the internal `DockFactory` (null-guarded close, capability stamping, host-window locator) is the single shared `Factory` instance — dock models back-reference the factory that initialized them, so there can be only one — held as a private detail by `Workspace`, `LayoutManager`, and the `WorkspaceViewModel` (which assigns it to the `DockControl`).
- Self-contained panels & reusable controls, each its own top-level folder: `Viewport/` (`CompositionInteropViewport.cs` is the D3D11/WGL interop surface), `WorldTree/` (`WorldTreeView`/`WorldTreeViewModel`), `EntityInspector/` (`EntityInspectorView`/`EntityInspectorViewModel`), `PropertyGrid/` (the generic grid: `PropertyNode` rows built by an `IPropertyNodeFactory` supplied to the grid, each row four slots — `[Left][Value][Right][Indicator]` — filled with slot view-models from `PropertyGrid/Slots/` (value editor, state indicator, list add/delete/reorder), each with its own view; `ReflectionPropertyNodeFactory` covers plain CLR graphs, domain leaf shapes it doesn't know plug in as `IValueEditor`s — the host view supplies the matching DataTemplate, so the grid stays domain-free — a list element carrying a non-empty string `Name` property labels its row with it instead of its index (rendered through `DisplayNameConverter`, which words-out identifier labels: "edit.openSettings" → "Edit Open Settings"), a value implementing `IDefaultSource` (Utils) supplies its own default twin for the state adorner where a default-constructed instance wouldn't do (a keybinding's default is its registered chord), read-only values render disabled/grayed with the warning-tinted lock, and at every level plain rows sort above the group bands — a leaf declared between two composites never renders sandwiched between their headers), `AssetOwners/` (the shared owner chrome: `AssetOwnerViewModel` carries the dirty-star `Title` + Save/Cancel and can host a real `Asset`'s dirty/save lifecycle; `AssetOwnerView` renders the owner's `Body` above the buttons), `MenuBar/` (`MenuBarViewModel`/`MenuBarView` — Edit ▸ Settings, Build ▸ project/Engine, Debug ▸ attach), `SettingsEditor/` (the Settings window: an asset owner whose body is two tabbed property grids over drafts — **Editor** (the `EditorSettings` draft, whose `Keybindings` section is the editor keymap surfaced as plain data — `EditorKeymap.CreateKeybindingDrafts()` fills the draft's `[JsonIgnore]` list, the standard reflection grid renders it like any other list with chords through the chord capture editor, and Save commits the sections through `SettingsManager.ApplyEditorDraftAsync` and the keybindings through `EditorKeymap.ApplyKeybindingsAsync`; the registry defines the editor's actions, so the list is read-only and each entry's name construction-only — only the chord edits, unlike a project `.inputmap` asset where everything does) and **Project** (the open project's `AppSettings` mirror via `AppSettingsDraft`, landed as whole-record pushes and saved through the asset; empty while disconnected); one Save lands every edited tab), `KeybindingsEditor/` (the chord-editing grid vocabulary, not a panel: `ChordCaptureBox` + the `ChordValueViewModel`/`ChordValueView` value-slot pair and `ChordValueEditor` — the `IValueEditor` that plugs chords into any `ReflectionPropertyNodeFactory`, e.g. a grid over an `.inputmap` asset), `Console/`, `LogConsole/`, `Game/` (`GameView`/`GameViewModel` — the Play/Stop/Pause game panel), `Toolbar/` (the viewport's movable overlay toolbar: the transform-tool radio row + snapping toggle as action-driven `ToolbarItemViewModel`s — clicks publish the same `EditorActionInvoked` the keybindings do, checked state re-derives from `GizmoToolChanged` — dockable against any viewport edge by dragging its grip (`ToolbarDockDrag` + the adorner-layer `DockDragIndicator`); the edge persists per viewport instance through the dock layout: the workspace gives an `IToolbarHost` view-model a `ToolbarPanelRecord` whose `ToolbarDockState` the view-model writes through (`ToolbarEdge`/`ToolbarDockState`/`IToolbarHost` live in `Utils/Toolbars/` so Workspaces never references the toolbar)), `AssetBrowser/`, `AssetViewer/`, `ContextMenu/`, `Status/`, `Ghost/`, `Searching/`, `ColorPickers/` (the color-editing controls), `Overlays/`, `ScriptEditor/` (the Monaco-backed editor; its vendored bundle is `ScriptEditor/Monaco/`, copied to output), `Behaviors/` (input/interaction glue; the micro-animation behaviors + `MotionTokens.cs` live in `Behaviors/Animations/`).
- `Resources/Templates/DefaultProject/` — a real on-disk project the editor copies and builds; not an embedded UI resource (`Resources/` also holds `Icons/` and the `AssetViewer/` preview assets, per the `AvaloniaResource`/`None` globs in the csproj).

### Key files to read first

- [`Launcher/Launcher.cs`](Launcher/Launcher.cs) — the entry point and DI composition root: `Launcher.LaunchAsync` boots Avalonia, configures the service provider, and runs the startup flow (project picker → splash → main window).
- [`Rpc/RpcClient.cs`](Rpc/RpcClient.cs) — the generic JSON-RPC transport (connection, retry, request/notification primitives); peer-agnostic.
- [`EngineApi/EngineRpc.cs`](EngineApi/EngineRpc.cs) — the engine connection: the engine-specific facade over `RpcClient` (handshake + typed notifications). The domain API surface lives on the `Entity`/`Component`/`AssetCatalog` constructs and the static `Asset` API that call its primitives.
- [`EngineApi/Session.cs`](EngineApi/Session.cs) — engine process lifetime (launch/attach/teardown).
- [`Utils/Attributes/DockableAttribute.cs`](Utils/Attributes/DockableAttribute.cs) — how panels are declared (a `[Dockable]` `XxxView` binds to `XxxViewModel` in the same namespace, or an explicit `ViewModel = typeof(...)`; slot/parent/float-bounds metadata rides on the attribute). Its view-model factory is authored in `Launcher.ConfigureServices` (`DockableFactories`) — dockable view-models are never registered as services.
- [`PropertyGrid/ReflectionPropertyNodeFactory.cs`](PropertyGrid/ReflectionPropertyNodeFactory.cs) — how a CLR object graph becomes slot-composed property rows (the factory pattern every grid source follows).
- [`Documentation/Architecture.md`](Documentation/Architecture.md) — the system narrative tying all of the above together.

## Build / Test / Run

```bash
# Restore + build (warnings are errors)
dotnet build Toybox.Studio.slnx

# Run; a Debug build enables the Avalonia dev tools (F12)
dotnet run --project Launcher/Launcher.csproj
```

Build artifacts go under `build/`. There is no unit-test project yet; verification is by building clean and running the app (see below).

The editor compiles and launches the engine itself. A Debug Studio drives a Debug engine, a Release Studio a Release engine. Studio needs a located engine checkout — if the `Locator` can't find one, set the **Engine path** in **Settings (⚙)**.

## Verification

- **Always build clean first.** `TreatWarningsAsErrors` is on; a warning fails the build. Fix all warnings.
- **Run the app and watch the logs.** Launch Studio, let it reach "Ready.", exercise the change, then shut down cleanly. Inspect `~/.toybox/Logs/TbxStudio.log` (the same stream shown in the in-app console) — resolve any logged warnings or errors and re-test until the log is clean.
- **Verify UI/rendering changes visually.** For viewport, theming, or layout changes, run the app and confirm the result on screen; a clean build alone is not proof for visual work.
- **Mind teardown.** Engine-session and plugin-owned resources have strict teardown ordering; if you touch `Session`, `EngineRpc`, or the viewport interop, verify a clean launch *and* shutdown with no orphaned engine process and no errors in the log.
